
#### 02 트랜잭션 고립화 레벨

고립화 (Isolation) 개념은 '데이터를 일관성 있게 **읽기**' 에 대한 개념이다.

오라클은 2레벨 (read committed)과 4레벨(serializable)만 공식적으로 지원하며, 3레벨은 for update 를 통해서 구현할 수 있다.

1. read uncommitted
	- 커밋되지 않은 데이터 읽기
	- 오라클은 Undo 로그를 기반으로 쿼리 시작시점 기준 커밋된 데이터를 읽으므로 해당되지 않는다. (MVCC 모델)
	- Dirty Read가 발생한다.

2. read committed
	- 오라클에서 문장 수준의 읽기 일관성만 따르는 레벨이다.
	- Dirty Read가 발생하지 않으나, Non-Repeatable Read 가 발생한다. 
		- Non-Repeatable Read
			- 트랜잭션 내에서 같은 데이터 읽기를 두 번 했는데, 데이터가 다름
			- txA가 레코드R 접근 → txB가 레코드R 변경 → txA가 레코드R 재 접근

3. repeatable read
	- 트랜잭션 안에서 같은 데이터를 다시 읽어도 일관성을 보장한다.
	- 오라클은 이 레벨이 따로 없으며 조회시 for update (row x-lock) 를 통해서 구현한다.
	- Non-Repeatable Read는 발생하지 않으나 Phantom Read 문제는 발생한다.
		- Phantom Read
			- 트랜잭션 처리 중 새로운 행이 추가됨 (insert) 에 따라 발생하는 이상 현상

4. serializable
	- Undo로그를 통해 트랜잭션 시작 시점의 SCN을 기준으로 데이터를 읽는다. 
		- read committed의 경우 쿼리 시작 시점의 SCN을 기준으로 데이터를 읽는다.
	- 트랜잭션 시작 이후 다른 트랜잭션이 커밋한 행을 갱신하려 하면 `ORA-08177`(can't serialize access) 에러를 반환하여 Lost Update를 방지한다.

>이상 현상은 '조회 → 조건 판단 → [수정]' 에서 데이터 일관성이 맞지 않게 되는 현상이다. 
>(수정 없이 읽기만 해도 일관성이 맞지 않을 수 있다.)

>오라클 serializable은 엄밀히 말하면 snapshot isolation 레벨이다. (write skew 못 막음)


#### 03 비관적 vs 낙관적 동시성 제어

- 비관적 제어
	- 읽을 때 락을 걸어서 충돌을 미리 차단한다.
	- for update [wait N | nowait] 이용 
- 낙관적 제어
	- 락을 사용하지 않으며 수정 시점에 변경 여부를 확인한다.
		- 전체 컬럼을 WHERE 조건으로 걸어서 확인할 수도 있고(NULL 위험), 버저닝 전용 컬럼을 따로 둘 수도 있다.
		- 수정 후 변경 여부를 확인했을 때, 다른 Tx에 의해 변경이 된 경우, 예외를 반환하거나 재시도를 하는 등의 처리는 어플리케이션 재량이다.

#### 04 동시성 구현 사례

- 예시 1 채번 테이블 동시성
	- 함수 안에서 번호를 올리고 **바로 커밋**하므로, 락이 즉시 풀리고 다음 세션이 곧바로 채번
		- 메인트랜잭션 종료까지 기다리지 않으나 Gap이 생길 수 있음
	- pragma autonomous_transaction (서브 트랜잭션을 따로 커밋하는 기능)

- 예시 2 선분 이력 정합성
	- for update를 부가서비스에 직접 거는 것이 아니라 상위 엔티티이며, 경합 가능성이 적은 고객 레코드에 거는 것이 인상적이었다.

#### 05 오라클 Lock

**래치와 버퍼락**

- 래치 
	- SGA에 있는 자료구조 보호 목적의 가벼운 Lock (해시 체인 탐색/변경 보호)
	- 대기 큐가 없으며 Spin & Sleep 방식

- 버퍼 Lock
	- 버퍼 블록에 대한 액세스를 직렬화 (shared / exclusive)

래치를 오래 잡으면 같은 체인을 쓰는 다른 세션이 모두 막히므로, 블록 작업은 버퍼 락으로 넘겨서 하는 구조


**Enqueue Lock**

- Enqueue Lock
	- 테이블, 트랜잭션, 테이블스페이스 등 공유 리소스에 대한 액세스를 관리한다.
	- 소유자와 대기자 목록을 관리. 큐 방식이므로 경합 순서를 보장한다.

- Enqueue 식별자
	- Type - ID1 - ID2로 식별한다.
		- 타입이 트랜잭션인 경우 
			- Type : Tx
			- ID1 : Undo 세그먼트 번호|트랜잭션 슬롯번호
			- ID2 : 트랜잭션 슬롯 Sequence 번호
		- 타입이 테이블인 경우 
			- Type : TM
			- ID1 : 오브젝트
			- ID2 : 0

##### TX Lock

**트랜잭션 종료(커밋/롤백)를 기다리기 위한 Enqueue 락**

사용 예 1. DML 로우 Lock

1. Tx1이 레코드 R을 변경
2. Tx2가 레코드 R변경을 시도하나, 레코드 행 헤더에 Lock Byte에 값이 있음. 
3. Lock Byte에 있는 값으로 블록헤더의 ITL 슬롯을 찾아감.
4. ITL 슬롯에서 XID (Undo 세그먼트 번호 + 트랜잭션테이블 슬롯 + 트랜잭션 SEQ) 값을 통해 트랜잭션 상태 정보를 찾아가고, 해당 트랜잭션이 Active 상태인지 확인한다.
	(Delayed Clean Out 케이스에서는 Active가 아닐 수 있음)
5. 트랜잭션이 Active 상태라면 TX Enqueue Lock 을 찾아가서, 대기자에 등록한다.
6. Tx1이 커밋/롤백하면 TX Lock이 해제되고, Tx2가 깨어나 진행한다.

추가로 오라클은 로우 Lock을 획득 시, 해당 테이블에 대한 테이블 Lock도 동시에 획득함으로써 현재 트랜잭션이 갱신 중인 테이블에 호환되지 않는 DDL 오퍼레이션을 방지한다.

사용 예 2. 유니크 제약 조건이 걸려있는 상태에서 앞선 트랜잭션이 커밋/롤백 되기를 기다릴 때

사용 예 3. ITL 슬롯이 부족해서 앞선 트랜잭션이 커밋/롤백 되고 ITL슬롯이 비워지기를 기다릴 때

사용 예 4. 인덱스 블록이 가득 차, 인덱스 분할을 하고 있는 선행 트랜잭션을 기다려야 할 때

> 인덱스 분할 작업을 하는 별도의 autonomous 트랜잭션 (서브 트랜잭션)을 분리해서 처리 하고 커밋한다. (메인 트랜잭션이 길어지는 것을 방지)


**TM Lock**

- 테이블 단위로 거는 Lock 이다.
- 락 모드가 매우 다양하고 호환 경우의 수가 많다.
- **테이블 Lock이 걸려있다고, 무조건 해당 테이블에 데이터 변경, 추가가 불가능 한 것이 아니며, Lock을 획득한 선행 트랜잭션이 어떤 작업을 수행하는 지를 알려주는 Flag이다.** 
- 예시) DML을 실행할 때 테이블 Lock을 걸며, 이 때 거는 Lock은 RX (row exclusive) Lock 이다.
