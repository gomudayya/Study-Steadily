#### 01 SQL과 옵티마이저 

SQL은 선언적인 언어. 상대적으로 추상적인 개념이다. 
따라서 SQL이 선언한 대로 데이터를 가져올 프로시저(Row Source)가 존재해야 한다. 

SQL은 하나지만 데이터를 액세스해서 가져오는 방법(실행계획)은 여러가지이다. 

- 어떤 순서로
- 어떤 조인방법으로
- 인덱스를 사용할지, 풀스캔을 할지

수백~수천개의 경우의 수가 생길 수 있으며, **데이터 딕셔너리에 쌓인 통계 정보를 기반으로 COST를 계산해
효율적인 실행계획을 찾아내는 것이 옵티마이저이다.**

참고) 가장 효율적인 실행계획이 아닐 수 있다. 옵티마이저 입장에서 가장 효율적인 실행계획을 찾는 비용이 클 것이라고 여겨진다면, 적당한 선에서 타협한 효율적인 실행계획을 고르는게 나을 수 있다.

#### 02 SQL 처리과정

1. 파싱
	- SQL의 구성요소를 분석해 문법/오브젝트/권한 체크 (파싱트리 생성)
	- **Shared Pool에 SQL 커서(공유커서) 가 캐싱되어 있는지 확인하며, 캐싱 되어 있으면 2, 3 과정을 생략할 수 있다.**
	- SQL문장 전체를 해시 키로 변환하여 캐시를 확인한다.

2. 최적화 (Optimization)

	- 여러 실행 계획 중 효율적인 실행계획을 찾는다.

3. Row-Source Generation

	- 옵티마이저가 만든 실행 계획에 기반해 실제 데이터를 액세스하는 소스를 생성한다.


재사용할 수 있는 SQL커서가 있어서 2, 3 과정을 생략할 수 있으면 **소프트 파싱**이며,
재사용할 수 있는 SQL커서가 없어서 1, 2, 3 단계를 모두 해야하면 **하드 파싱**이라고 부른다.

#### 03 라이브러리 캐시 구조

최적화(Optimization) 단계는 고비용이다. Row-Source까지 기껏 만들어 놓고, 한 번 쓰고 버리기에는 비용적으로 아깝다. 그래서 라이브러리 캐시라는 곳에 Row-Source를 캐싱한다. 

이 때, Row-Source만 캐싱하는 것이아니라 다른 요소(실행 통계, 옵티마이저 환경정보)들도 필요에 의해 같이 캐싱을 하게 되는데 통틀어서 이것을 **SQL커서**(**공유 커서**) 라고 부른다. 

라이브러리 캐시 또한 블록 버퍼 캐시와 같이 해시를 이용한 캐시이며 래치(뮤텍스) 경합이 발생한다.
SQL커서 이외에도 PL/SQL, 테이블, 인덱스 등의 오브젝트 정보들도 저장하게 된다. 이들을 통틀어 라이브러리 캐시 오브젝트(LCO) 라고 부른다.

#### 04 커서 공유

###### 커서

- 공유 커서 : 라이브러리 캐시에 저장되는 SQL커서 (실행 계획)
- 세션 커서 : PGA에 저장되는 커서 (실행 상태 : 바인드 변수, fetch 상태, 조인작업 등)
- 애플리케이션 커서 : 세션 커서를 가리키는 핸들 (JDBC기준 Statement/PreparedStatement 객체)

실행순서 관점으로 보면 아래와 같다.

1. Open: 애플리케이션이 커서를 열면 PGA에 세션 커서가 할당되고, 애플리케이션은 핸들을 받는다.
2. Parse: 상황에 따라 하드파싱 or 소프트파싱이 발생하며,  세션커서는 공유커서를 가리킨다.
3. Bind/Execute: 세션 커서에 바인드 값을 넣고, 공유 커서의 실행계획대로 실행한다.
4. Fetch: 애플리케이션 커서로 결과를 읽는다. 몇 번째 행까지 읽었는지는 세션 커서가 기억한다.
5. Close: 애플리케이션 커서와 세션 커서는 닫히지만, 공유 커서는 라이브러리 캐시에 남는다. (LRU)

공유커서는 엄밀히 하면 다시 Parent커서 (1)와 Child커서 (N)로 나뉜다.

- Parent 커서
	- SQL 텍스트 단위
	- Parent 커서를 공유하지 못하고, 추가로 만드는 상황
		- 주석, 대소문자, 줄바꿈 등 SQL 텍스트가 조금이라도 다르면 모두 새로만든다.

- Child 커서
	- 실행 환경 정보 단위 (실행환경, 옵티마이저 설정값, 참조오브젝트의 상태)
	- Child커서를 공유하지 못하고, 추가로 만드는 상황
		- 오브젝트 명이 같지만 실행한 사용자에 따라 다른오브젝트를 가르킬 때
		- 옵티마이저 모드가 다를 때
		- 바인드 변수의 타입이 다르거나,  길이가 크게 다를 때

Parent커서 뿐 아니라 Child커서를 새로 만드는 상황에서도, 최적화와 Row Source생성을 다시 해야 한다.

#### 05 바인드 변수의 중요성 (하드파싱 생략)

바인드 변수를 사용하지 않고, 리터럴을 사용하면 Parent커서를 공유하지 못해 하드파싱이 계속 발생한다.
바인드 변수를 사용하면 동일한 SQL 텍스트 단위로 인식하여 소프트파싱을 할 수 있다.

바인드 변수의 파라미터값만 바뀌는 쿼리들이 반복적으로 사용되는 OLTP 환경 에서(트래픽까지 많다면),
하드 파싱이 계속 발생하는것은 데이터베이스 성능에 매우 치명적이다. 

치명적인 이유
- 최적화(Optimization) 단계와 Row Source 생성에 드는 CPU 소모
- Shared Pool 메모리 낭비로 인한 캐시 공간 부족
- 캐시공간에 커서를 계속 등록하므로 Shared Pool, 라이브러리 캐시의 래치 경합 증가

>IN_LIST의 개수가 다르면 다른 SQL로 인식되어 하드파싱을 해야한다. Hibernate에서 Batch Size옵션을 지정하면 실제 파라미터 외에 IN절에 NULL을 꽉 채워가며 사이즈를 고정으로 맞추는데 이는 하드파싱 생략을 위한 최적화 목적이다.

#### 06 바인드 변수의 부작용과 해법

바인드 변수를 사용하면 하드 파싱 시점에 값을 알 수 없어서, 컬럼 히스토그램 통계를 활용할 수 없다.
컬럼의 데이터 분포가 균일하다면 크게 문제가 없지만, 컬럼값 별로 선택도가 극단적으로 분포되어 있다면, 풀스캔이 유리한 상황에서 인덱스를 타는 등의 (혹은 그 반대) 문제가 생길 수 있다.

**부작용에 대한 해법**

- 바인드변수 Peeking
	- 하드파싱 할 때, 바인드 변수 값을 살짝 훔쳐 보고 컬럼 분포를 이용해 실행계획을 결정함.
	- 처음 들어온 값 기준으로 실행계획이 고정되고 쿼리 실행시간이 들쭉날쭉 하여 쓰기 어려움

- **적응적 커서 공유**
	- 바인드 변수 Peeking에서 개선된 기능이고 기존 고정적인 실행계획과 달리 '적응적' 이다.
	- 바인드 변수값과 컬럼분포를 보고 Child커서를 새로 만들지 말지를 판단한다.
		- 특정 바인드값에서 이전보다 일량 변동이 심할 때 Bind Sensitive에서 Bind Aware모드 전환.
		- Bind Aware모드에서는 매 실행마다 선택도를 확인해 Child커서를 고르거나 새로 만든다.

- 입력값에 따라 SQL 분리 및 힌트 선택 (필요하면 어쩔 수 없지만 유지보수하기 썩 좋은방식은 아님;;)

- OLTP성 프로그램이 아니라 배치, DW, OLAP 프로그램이라면 라이브러리 캐시 재사용의 이점이 적으니, 바인드 변수가 아닌 Literal 상수를 사용하는 것이 더 나을 수 있다.  
	- 수행 빈도가 낮고 1회 수행 시간이 긴 SQL인 경우에는 리터럴이 낫지만
	- 같은 SQL을 반복 실행하는 배치는 바인드 변수 사용이 나을 수 있다.


#### 07 세션 커서 캐싱 (softer soft parse)

바인드변수를 이용한 효과는 하드파싱을 생략하는 것이다.
세션커서를 캐싱하는 효과는 소프트파싱의 비용을 줄이는 것이다. 그래서 softer soft parse 라고 한다.

>세션 커서를 캐싱하면 syntax, semantic 체크와 해시 버킷 탐색을 생략할 수 있다. 다만 캐싱된 커서가 유효한지 확인하러 라이브러리 캐시에 접근은 하므로 소프트 파싱으로 집계된다.

**session_cached_cursors**

- 얼마나 많은 세션 커서를 캐싱할지를 지정하는 파라미터
- 커서를 닫을 때, 해당 커서의 Parse Call 횟수를 확인해 그 값이 3이상 이면 세션 커서 캐시로 옮긴다.
	- 세션 커서 캐시는 PGA 안의 공간이다. 공유 캐시가 아니기때문에 경합이 없고, 접근비용이 적다.

#### 08 애플리케이션 커서 캐싱

어플리케이션 커서(세션커서의 핸들) 는 자바 기준 Statement 객체에 해당한다.

바인드 변수를 통한 하드파싱 생략과 세션커서를 통한 Softer soft parse는 Parse Call을 줄여주지 않지만,
어플리케이션 커서 캐싱은 Parse Call 자체를 줄여준다. (Parse 과정 생략)

자바에서는 PreparedStatement 객체를  반복문 밖에서 생성하고, 반복문 안에서 같은 쿼리를 execute하게 되면 Parse Call 자체가 생략된다. 또는 반복문 안에서 PreparedStatement 객체를 생성하더라도 묵시적 캐싱 기능을 사용해도 Parse Call이 생략된다. 

묵시적 캐싱 : `setImplicitCachingEnabled(true)`, `implicitStatementCacheSize` 설정

PL/SQL 내부의 SQL은 PL/SQL 엔진(어플리케이션 느낌)이 커서를 열어둔 채 재사용 해 ParseCall이 발생하지 않는다.

#### 09 Static SQL vs Dynamic SQL

- **Static SQL**: 코드에 SQL이 고정으로 박혀 있어 컴파일할 때 이미 확정된 SQL. 
- **Dynamic SQL**: 실행 중에 문자열로 조립해서 만드는 SQL. 자바는 전부 JDBC를 이용하는 String 기반이기 때문에 Static SQL을 사용할 수 없으며 모두 Dynamic SQL에 해당된다.

이 두 용어는 정확하지 않게 사용되는 경우가 많다.

트레이드 오프를 고려한 쿼리를 어떤식으로 작성해야 하는지에 대한 내용이다.
