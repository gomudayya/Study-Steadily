
### 이벤트 드라이븐 아키텍처?

시스템이 **실시간 이벤트가 발생하는 즉시 이를 감지하고, 처리하고, 관리하며, 반응할 수 있도록 하는 소프트웨어 설계 패턴** (이하 EDA로 표현)

**이벤트가 발생하는 순간**, 해당 이벤트에 대한 정보가 **실시간으로 반응해야 하는 모든 애플리케이션, 시스템 에게 전달된다.**

이벤트?
→시스템 내에서 발생한 중요한 상태 변화를 나타내는 **메시지**
ex) 주문 생성, 사용자 탈퇴 등등

### 왜 이벤트 드라이븐 아키텍처를 사용하는가

이벤트 드라이븐 아키텍처의 장점은 다음과 같다.

- 각 시스템과 컴포넌트간의 느슨한 결합
- 독립적인 개발과 배포
- 확장성

이러한 구조적 이점을 가질 수 있는 이유는, 이벤트 프로듀서는 어떤 소비자가 이벤트를 처리하는지 알 필요가 없고, 이벤트 소비자도 어떤 생산자가 이 이벤트를 생산하는지 몰라도 되기 때문이다. 소비자는 이벤트가 발생한 것만 알고 처리하면 되고, 생산자는 이벤트를 만들기만 하고 이후의 과정은 알필요가 없다.

또한 이러한 구조적 이점 이외에도, 작업을 비동기적으로 처리할 수 있어 응답성 향상될 수 있다.

### 이벤트 드라이븐 아키텍처의 단점

하지만 모든 기술의 트레이드 오프가 존재하듯이 EDA도 마찬가지이다.

- 시스템 전체 동작을 파악하기 어렵다. (시작, 완료, 어떤서비스들이 메시지를 주고받는지)
- 데이터 복제가 많아지고 최종적 일관성을 감수해야 한다. 
	- 강한 일관성이 꼭 필요한 서비스라면 
- 운영 관리 비용 증가
	- 이벤트가 여러개 생성될 경우를 대비한 멱등 처리
	- 이벤트 순서 처리 문제
	- 디버깅 모니터링 에러 복구등의 난이도 및 학습곡선 증가

##### 다른 인스턴스간의 프로세스 통신이 필요할때 이벤트 드라이븐 아키텍처만이 답인가?

그렇지 않다. 위의 단점을 감수하고서라도 내가 해결해야하는 문제에 이벤트 드라이븐 아키텍처가 꼭 필요한가? 는 생각해 보아야 한다. 아래는 인스턴스간 통신에서 사용할 수 있는 다른 방법들이다. 

- 동기 RPC(Remote Procedure Call) 호출 
	- REST API
	- gRPC
- 공유 데이터스토어 방식
	- 데이터베이스 폴링
	- SP를 통한 간접 통신

공유 데이터스토어 방식은 레거시 시스템에서 자주 쓰이지만 색안경을 끼지 않고 바라보면 나름의 장점이 존재하는 것 같다. 관리하기가 수월하며 별도의 인프라 비용이 필요하지 않다. 중소규모의 서비스이고, 시스템의 확장이 잘 일어나지 않고 사용자 풀도 고정적이라면 굳이 많은 비용을 감수하며 EDA를 선택할 필요가 있을까? 라는 생각이 든다.

### 채팅 서비스에서의 EDA 적용 

**채팅 메시지 팬아웃**

- 유저가 메시지를 보내면 방의 모든 유저에게 전달해야 한다.
	- 다중서버 환경이고, 웹소켓을 사용한다면 유저가 어느 서버에 연결되어 있는지 모른다.
	- 발신 서버는 수신 서버가 누군지 모르고, 이벤트만 발행하도록 한다.
- 단순히 채팅 메시지 뿐만 아니라, 서버에서 클라이언트로 푸시해야 하는 모든 데이터들이 팬아웃 대상이다. 
	- 사용자 입장 퇴장, 채팅방 정보 변경, 메시지 읽음 처리, 유저 on/off 상태 표시 등

**푸시 알림**

- 유저가 오프라인 상태인 경우, 알림 수신을 허용한 이벤트(채팅 메시지, 멘션, 초대 등)에 대해 푸시 알림을 보낸다.
